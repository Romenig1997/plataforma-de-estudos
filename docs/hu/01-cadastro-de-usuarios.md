# HU01 — Cadastro de Usuários

**Status:** Concluída
**Dependências:** Etapa 0 (estrutura inicial)

## Objetivo

Permitir que um candidato crie a própria conta na plataforma.

## Critérios de aceite

| # | Critério | Verificação |
|---|----------|-------------|
| 1 | Cadastro válido é concluído com sucesso | `201` + `Location` + corpo com `id`, `nome`, `email` |
| 2 | Nome é obrigatório | `400`, erro no campo `nome` |
| 3 | E-mail é obrigatório | `400`, erro no campo `email` |
| 4 | Formato de e-mail inválido é recusado | `400`, erro no campo `email` |
| 5 | Senha com menos de 8 caracteres é recusada | `400`, erro no campo `senha` |
| 6 | E-mail duplicado é recusado | `409`, erro no campo `email` |
| 7 | O cadastro é persistido no banco | Registro lido de volta pelo `UsuarioRepository` |

Regras transversais: a senha nunca é retornada na resposta e nunca é
gravada em claro; e-mail é normalizado (`trim` + minúsculas) para que
`Ana@Email.com` e `ana@email.com` sejam a mesma pessoa.

## Schema

Definido em `backend/src/main/resources/schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS usuario (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome       VARCHAR(120) NOT NULL,
    email      VARCHAR(180) NOT NULL,
    senha_hash VARCHAR(255) NOT NULL,
    CONSTRAINT uk_usuario_email UNIQUE (email)
);
```

Decisões:

- **Sem `data_criacao`.** Não estava no escopo acordado; a HU que precisar
  de auditoria adiciona a coluna.
- **`senha_hash`, não `senha`.** O nome do coluna é a documentação mais
  clara possível sobre o que fica gravado.
- **`ddl-auto: validate`.** O Hibernate não cria nem altera nada: se o
  `schema.sql` e a entidade divergirem, a aplicação falha ao subir em vez de
  assumir uma estrutura errada em produção.
- **SQL compartilhado entre H2 e PostgreSQL**, com `IF NOT EXISTS`, para
  que os testes validem o DDL real.

## Endpoint

`POST /api/usuarios`

Requisição:

```json
{ "nome": "Ana Souza", "email": "ana@email.com", "senha": "senha1234" }
```

Sucesso — `201`, header `Location: /api/usuarios/{id}`:

```json
{ "id": 1, "nome": "Ana Souza", "email": "ana@email.com" }
```

Erro — `400` (validação) ou `409` (e-mail duplicado), mesmo formato:

```json
{ "erros": [ { "campo": "email", "mensagem": "Ja existe um usuario cadastrado com este e-mail." } ] }
```

Um formato único para 400 e 409 é intencional: o frontend exibe a mensagem
próxima ao campo sem tratar dois contratos diferentes.

## Hash de senha

PBKDF2-HMAC-SHA256 via `javax.crypto` (`CodificadorDeSenha`), sem Spring
Security e sem dependências extras. O código gravado carrega o custo usado
na geração, permitindo aumentá-lo depois sem invalidar senhas existentes:

```
pbkdf2-sha256$<iteracoes>$<salt base64>$<hash base64>
```

- Produção: 210.000 iterações (`plataforma.senha.iteracoes`).
- Testes: 1.000 iterações — o custo se paga a cada cadastro e não agrega
  nada no teste.
- Salt de 16 bytes aleatórios por senha; comparação em tempo constante
  (`MessageDigest.isEqual`).

## Frontend

`frontend/src/App.tsx`: formulário controlado com `fetch` nativo, sem
biblioteca de formulário e sem router.

- Erros por campo vindos da API, exibidos abaixo do input correspondente.
- `aria-invalid`, `aria-describedby`, `role="alert"` e `aria-live`.
- Campos e botão desabilitados durante o envio, com feedback "Cadastrando...".
- Em sucesso, exibe o `id` gerado e limpa o formulário.
- Erro de rede recebe mensagem própria, distinta dos erros de validação.
- `frontend/vite.config.ts` faz proxy de `/api` para `localhost:8080`,
  evitando CORS no dev e mantendo a mesma URL em produção.
